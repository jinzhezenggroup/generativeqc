# Decision: retain shared high-order weighted CUDA arithmetic

Status: implemented; complete wheel and scheduled-device endpoint gates pending
Date: 2026-11-16

## Problem

The contained wheel failure documented in
`../../proposed/2026-11-16-wheel-direct-fallback-compiler-oom.md` establishes a
12-GiB container OOM during Direct fallback compilation. Response-kernel pooling
occurs later in the build graph and cannot by itself fix this earlier owner.

Large order-four/five weighted scalar roots were forced inline into native
spin, radial, output-layout and precision adapters. Keeping their source in
generated headers did not imply sharing their optimized compiler working set.

## Decision and invariants

Emit header-safe `__device__ inline __noinline__` callables for the large
order-four/five scalar bodies: 22 and 24 respectively. The public scalar emitter
exposes an explicit `cuda_noinline` choice. Small/default CUDA helpers and CPU
emission retain their original behavior. In particular, the complete low-order
weighted header remains unchanged.

Keep the complete-class wrappers inline and preserve their original
64-component partitions, global weight indices and addition order. Retain all
strict FP64, explicit FP32, relative-response and pair-separable variants. Native
screening, density contractions, source layout, radial identity, retry policy,
queue ownership, diagnostics, angular coverage and bounded fallbacks are not
changed. This does not merge distinct scientific graphs or remove methods.

## Complete-object evidence

The comparison covers the complete `direct_bounded_fallback.cu` object, not an
isolated math helper. It uses NVCC 12.9.86, verified sccache 0.16.0, `sm_80`,
`-O3 -DNDEBUG -std=c++20 -rdc=true`, PIC and the production
`-Xptxas=--disable-optimizer-constants` option. Both requests use the existing
cache and report zero hits, four CUDA-stage misses and zero compiler failures.

| Complete fallback owner | Original | Shared arithmetic |
| --- | ---: | ---: |
| PTX bytes | 153,750,985 | 149,129,566 |
| Kernel entries | 108 | 108 |
| Retained device functions | 501 | 525 |
| Object bytes | 76,439,632 | 66,620,976 |
| Compiler-tree maximum RSS, KiB | 8,772,148 | 5,579,972 |
| Owned compiler-server lifetime, seconds | 1,199.78 | 1,278.34 |

All 108 mangled kernel entry identities match. The source comparison allows only
the callable qualifier changes: every other generated byte, including arithmetic
and partition reductions, matches the parent. These are retained one-off audit
results, not permanent source-body fingerprints or private-name CI ratchets.

GNU time wraps an owned foreground sccache server and includes its reaped
compiler children. This is genuine worker maximum RSS, not the lightweight
sccache client's RSS, and is not a sum of concurrent workers or a container
peak. The measured maximum drops about 36.4%, from 8.37 to 5.32 GiB; the object
shrinks about 12.8%, while PTX shrinks only about 3.0%.

The baseline harness's shell tail encountered a parse error after its compiler
completed because the running instrumentation script had been edited. Its
client-duration field is discarded. The complete object, zero compiler failures
and GNU-time server report establish completion and worker RSS. The table uses
the same server-lifetime measurement on both sides, including small harness
startup/teardown overhead. Independent host tests and other compiler probes
overlap portions of these runs. They are not an uncontended timing benchmark.
In particular, **this experiment does not demonstrate faster compilation**.

The affected class-domain object also compiles against the shared headers, and
both complete objects pass a combined `sm_80` NVCC device link. The
existing bounded Direct device-link owner, not the non-RDC resident angular-force
owner, remains responsible for coalescing identical device symbols. Complete
three-architecture wheel acceptance remains a separate gate: one local `sm_80`
sample cannot prove that two concurrent wheel compilers fit the 12-GiB envelope.

## Scientific and ownership gates

The focused independent weighted/native/range suite passes 568 tests. It covers
Libcint references, all high-order component partitions, both spins, combined and
separate sources, multiple radial parameters, explicit precision/retry behavior,
screening and range launch forwarding. A new executable two-owner host shim
preserves actual noinline and inline linkage while checking scalar results and
all four-center derivatives against the IR interpreter. Compiler structure:
604 modules, zero dependency errors. Ruff checks and formatting pass.

An additional RDC CUDA probe compiles and links the original and new complete
high-order strict/mixed/relative and separable callables. Its caller register or
spill report does not establish a complete call-tree or endpoint improvement.
Finite Slurm job 12282 could not start: the only local `main` node reports
`drained / maintenance`. The owned pending job was cancelled, without bypassing
Slurm or changing device visibility. No physical GPU numerical, complete Direct
endpoint timing or runtime nonregression is claimed. Those gates must pass on an
authorized available scheduler allocation before treating this as fully qualified.

## Rejected alternatives and follow-up

- A giant unity source increases the already-large compiler working set.
- Dropping methods, high-angular/range fallbacks, scientific tests or wheel
  architectures changes the product rather than reducing duplicated work.
- Removing the container bound hides the confirmed resource failure.
- Outlining small low-order helpers without endpoint evidence risks hot-path
  regressions; they deliberately retain their current generated output.
- Calling this a broad compile-time fix would be misleading: the remaining
  149-MB PTX and many native density/component-loop specializations still need
  investigation. Shared weight preparation across numerical variants is a
  candidate, subject to preserving screening, reduction order and all fallbacks.

Revisit with complete wheel cache/resource diagnostics and scheduled-device
scientific plus complete-endpoint timing. Do not infer wheel success or runtime
speedup from source sharing, caller registers or one compiler's maximum RSS.
