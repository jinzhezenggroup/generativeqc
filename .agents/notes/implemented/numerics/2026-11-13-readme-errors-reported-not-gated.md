# Decision: README HF/DFT benchmarks report errors instead of gate counts

Status: implemented
Date: 2026-11-13

## Problem

The README HF/DFT cohorts published two win counts: all pairs (for example
H100 62/64 cold) and "qualified" pairs that passed fixed acceptance gates
(E/atom ≤1e-5 Eh, Fmax ≤1e-4, Frms ≤3e-5 Eh/Bohr; for example 56/58). Readers
could not tell which count was the claim, and "six failing pairs" suggested
that an implementation was wrong.

The retained samples show otherwise. In both the RTX 5090 #3072 cohort and the
H100 `a7241b4fd` cohort, the six "failing" pairs (DF HF at all sizes,
Direct/DF M06-2X3) have nearly the same errors in both engines. Call by call
(cold with cold, warm with warm), the two engines' errors differ by at most
1.6e-9 Eh/atom and 3.5e-6 Eh/Bohr (maximum force component), far below the
1e-5 / 1e-4 gate scales. These errors come from the shared default settings
(JKFIT fitting error, default XC grid), not from either implementation.
Relative agreement is not uniform: Direct ωB97M-V12 RMS force errors are
2.6e-6 versus 1.9e-6 (37%), and Direct r2SCAN-3c3 cold maximum-component
errors 1.34e-5 versus 0.99e-5 (35%), so absolute bounds are the published
statement. The unthresholded "1,024 cross-engine vector comparisons pass"
claim was dropped as an implicit gate.
The GPU4PySCF publication likewise reports errors without pass/fail gates.

## Decision

The README and the linked cohort READMEs compare timings for all 64 pairs. For
every pair they report both engines' largest energy/force errors against the
common dense Direct reference, in `errors.md`. This table is generated by
`benchmarks/readme_defaults_summary.py --error-table` and tested against the
hashed `samples.json.xz`.

The replayed `audit()` summary and the manifests still contain the historical
gate counts, so the archived summaries replay byte-for-byte. Those counts are
no longer a publication claim.

This decision does not relax the development rule. Numerical, precision and
derivative changes still need an independent oracle and explicit acceptance
gates appropriate to the method (`AGENTS.md`). That rule governs changes to the
code, not this public benchmark presentation.

## Rejected alternatives

- **Keeping the gate counts as the headline.** They mislabel shared, setting-
  intrinsic errors as failures and invite comparing two different win counts.
- **Replacing the GPU4PySCF-produced dense reference with Psi4 for all
  pairs.** At Psi4 master (checked 2026-11-13), `VBase::vv10_nlc_gradient`
  throws ("Cannot compute VV10 gradient contribution"), so there are no
  analytic ωB97M-V forces. The released options also have no XC grid-weight
  response (`DFT_GRID_RESPONSE` appears only in development builds), whereas
  this reference and both engines include grid response. A third-party
  reference remains possible as a cross-check: ORCA or Q-Chem for ωB97M-V, and
  Psi4 for the other methods after measuring the grid-response term.

## Revisit when

- A publication needs an accuracy-matched speed comparison, for example an
  error–time Pareto front, rather than reported errors.
- Psi4 or another independent code supplies VV10 gradients and grid-response
  forces, so that a single third-party reference covers all eight methods.
